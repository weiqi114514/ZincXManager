## 一、玩家 ID 体系

| 类型 | 格式 | 例子 |
| --- | --- | --- |
| 官方端本地账户 | `ZXMOS-<编码>` | `ZXMOS-5` |
| 子服账户 | `ZXMS-<osuser>-<osid>-<编码>` | `ZXMS-ZES-1-14` |

- **服务端 ID**：`ZXMS-<osuser>-<osid>`；官方端没有短名和编号，服务端 ID 就是 `ZXMOS`。
  - `<osuser>` = 该子服在 ZXMOS 上注册的账号名（实测 `testserver`；用户举例 `ZES`）。
  - `<osid>` = 该账号在 ZXMOS 的账号 ID（`AccountLoginAck` 回执 `ok|<账号名>|<id>|<等级>` 的第三段，可缓存成只读配置 `osid`）。
- **编码**：账户在所属服务端内部的数字 ID，各服务端独立（`ZXMS-ZES-1` 的 1 和 `ZXMOS` 的 1 是两个人）。
- **ZXMC 主界面左下角**：仍只显示编码（`ID: 4`），不显示前缀。
- **聊天窗侧栏「对象 ID」**：显示完整 ID（`ZXMS-ZES-1-14` / `ZXMOS-5`）。

## 二、存储结构（服务端根目录下）

```
User/
└─ Friend/
   └─ <服务端ID>/
      └─ <本账户编码>/
         ├─ FriendList.dat          ← 好友列表
         └─ Ch/
            └─ <对方完整玩家ID>.dat ← 与该好友的聊天记录,一人一个文件

IMG/
├─ PictureList.dat                  ← 图片对照表(聊天图,头像不进表)
├─ ChatIMG/                         ← 聊天图片文件
└─ UserIMG/                         ← 头像文件
```

官方端本地账户的目录名用 `Local`（实测 `User/Friend/Local/5/FriendList.txt`），对外玩家 ID 仍是 `ZXMOS-5`。

### `FriendList.dat`

- UTF-8 无 BOM，CRLF，末尾可留一个空行；无表头。
- 每行：`<服务端ID>` + **一个空格** + `<该服务端上的账户编码>`。

```
ZXMS-ZES-1 1
ZXMS-HT-2 23
ZXMOS 5

```

读取时容忍空行、行首行尾空格、多余空行。

### `Ch/<对方完整玩家ID>.dat`

- UTF-8 无 BOM，CRLF；末行有无行尾都容忍。
- 每行：`<时间>` + 空格 + `<ME|YOU>` + 空格 + `<内容>`。
- 时间格式：`yyyy-MM-dd HH:mm:ss`（如 `2026-10-31 14:22:05`）。
  - 历史文件是旧的三段式（`2026 14 10 YOU 你好`），读取时要兼容，写新行一律用完整时间戳。
- 图片消息行：`<yyyy-MM-dd HH:mm:ss> <ME|YOU> IMG <IMG/ChatIMG 下的文件名>`。
- 内容里的换行落盘前替换掉。

---

### `logs/friend/<yyyy-MM-dd>.dat`（好友日志，ZXMS 与 ZXMOS 各一份）

- 记录所有人的加/删/同意/拒绝动作，给管理员查。
- **按天分文件**：一天一个，文件名就是日期，如 `logs/friend/2026-10-31.dat`；跨天自动开新文件。
- 目录不存在时自动创建；ZXMS 与 ZXMOS 各自根目录下都有一套 `logs/friend/`。
- UTF-8 无 BOM，CRLF。
- 每行五段，Tab 分隔（时间写全，方便跨文件合并分析）：

```
<时间 yyyy-MM-dd HH:mm:ss>	<动作>	<操作者玩家ID>	<对方玩家ID>	<备注>
```

- 动作取值：`add`（直接加好友）、`request`（发出申请）、`agree`（同意）、`reject`（拒绝）、`remove`（删除好友）。

```
# 文件: logs/friend/2026-10-31.dat
2026-10-31 15:30:12	add	ZXMS-ZES-1-14	ZXMS-HT-2-23	直接加好友
2026-10-31 15:31:02	request	ZXMOS-5	ZXMS-ZES-1-14	想加你一起调服务器
2026-10-31 15:32:40	agree	ZXMS-ZES-1-14	ZXMOS-5	
```

### 好友关系与留档（已定）

- **好友关系双向**：同意后双方各写一行到自己的 `FriendList.dat`；删除同理，两边都删。
- **聊天记录在 ZXMOS 留档**：跨服聊天由 ZXMOS 中转时，官方端也落一份（`User/Friend/<对方服务端ID>/<编码>/Ch/…` 的同构结构），子服本地仍保留自己那份。

## 三、图片

### 目录与命名

| 类型 | 子服 | 官方端 |
| --- | --- | --- |
| 聊天图 | `ZXMS-<osuser>-<osid>-<发送者编码>-<图片ID>.<ext>` | `ZXMOS-<编码>-<图片ID>.<ext>` |
| 头像 | `ZXMS-<osuser>-<osid>-<账户编码>.png` | `ZXMOS-<编码>.png` |

- 图片 ID：服务端 6 位自增（`000001` 起）。
- 扩展名保留原图。
- 上限 8 MB（`imgmaxkb` 可配）。

### `IMG/PictureList.dat`（对照表）

- UTF-8 无 BOM，CRLF，末尾可留空行。
- 每行四段，**Tab 分隔**（时间里有空格，空格分隔切不开）：

```
<图片文件名>\t<发送者完整玩家ID>\t<接收方完整玩家ID>\t<发送时间 yyyy-MM-dd HH:mm:ss>
```

```
ZXMS-ZES-1-14-000001.png	ZXMS-ZES-1-14	ZXMS-HT-2-23	2026-10-31 15:09:00
ZXMOS-5-000007.png	ZXMOS-5	ZXMS-ZES-1-14	2026-10-31 15:10:12
```

- **头像不进这张表**。
- 子服与官方端各存自己的一份。
- 用途：①反查这张图是谁发的、发给谁；②分配下一个 6 位图片 ID（扫表里最大值 +1）；③清理过期文件时同步删表行。

### 配置项（ZXMS / ZXMOS 各一套）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `img` | 1 | 是否允许发图片 |
| `imgmaxkb` | 8192 | 单张上限（KB） |
| `imgdaymax` | 50 | 每人每天最多发几张 |
| `imgbandkbs` | 2048 | 图片传输带宽上限（KB/s），0 = 不限 |
| `imgkeepdays` | 30（暂定） | 图片保留天数，0 = 永不删除 |

传输按 64 KB 分块 + 令牌桶限速。

### 过期清理

- 按 `imgkeepdays` 扫描 `PictureList.dat`：到期的删文件 + 删行。
- 对不上号的只记 Warn，不主动删文件：
  - 表里有、盘上没有 → 删行；
  - 盘上有、表里没有 → Warn（可选补录）。

### 跨服与中转

- 跨服看图、聊天、加好友都走 ZXMOS 中转。
- 发送权限：谁都能发。

## 四、账户名规则

- ZXMS 账户名（`osuser` 与本服账户名）只能由英文、数字、下划线组成：正则 `^[A-Za-z0-9_]{2,32}$`。
- 要向玩家展示中文，用 `linkname=0` + `name=<中文>`（`linkname≠0` 时展示名 = `osuser`，代码见 `ZincXManagerServer/Program.cs:188 ResolveName`）。
- **不新增** `displayname` 配置项（早期方案已作废）。
- 老账户里的中文名：启动时只记 Warn，不强制改名。

## 七、开发流程（每个功能都按这个走）

单人 + AI 的开发流程，目标：**每一步都有可验收的产物，不靠记忆**。

### 步骤总览

```
① 需求入档 → ② 设计定稿 → ③ 分层实现 → ④ 单测 → ⑤ 全量回归
   → ⑥ 真机联调 → ⑦ 文档同步 → ⑧ 打包发版 → ⑨ 沉淀
```

任何一步没过，不进入下一步；发现问题回到对应步骤，不跳步。

### ① 需求入档

- 需求方口述 → 写进本文件对应章节（格式、边界、默认值）。
- 有歧义当场问，**不问不写代码**。
- 产出：本文件里新增/修改的条目。
- 验收：需求方点头「就这么做」。

### ② 设计定稿

- 数据结构：文件路径、文件名、行格式、编码、行尾，写成「例子 + 反例」。
- 协议：先查 `ZincXManagerShared/Network/Protocol.cs` 现有码段，挑空闲段（如 640–645），**业务代码不写死数字**。
- 配置项：键名小写、模块前缀（`img*`），给默认值和取值范围，补进 ZXMS/ZXMOS 的配置项表。
- 产出：本文件「结构 + 格式 + 协议 + 配置」四块定稿。
- 验收：能照着这份文档写出读写代码，不需要再问。

### ③ 分层实现

严格按依赖顺序，每层自带单测：

| 顺序 | 层 | 放什么 | 不许放 |
| --- | --- | --- | --- |
| 1 | Shared | `PlayerId`、`FriendStore`、`ChatStore`、`ImageStore`、协议常量 | 业务判断、UI |
| 2 | ZXMS | 绑定/白名单/进服链路里调用上面这些、配置项、控制台命令 | UI、MC 世界 |
| 3 | ZXMOS | 账号、中转、官方端存储 | 子服专属逻辑 |
| 4 | ZXMC | 界面、调协议、显示 | 读写服务端文件、业务规则 |
| 5 | ZXMM | 只上报事件、只执行被调用的方法 | 任何判断/缓存/本地文件 |

- 每写完一层跑一次 `dotnet build <该工程>.csproj -c Debug`，0 错误再往下。
- 提交信息：`feat(模块): 做了什么` / `fix(模块): 修了什么`，一次提交只做一件事。

### ④ 单测

- 新增套件放 `tests/ZincXManagerTests/<模块>Suite.cs`，在 `Program.cs` 里注册。
- 必须覆盖：正常路径、脏数据（BOM/空行/多余空格）、边界（空集合、超长、重号）、跨服务端隔离、过期清理。
- 临时目录用 `Directory.SetCurrentDirectory` 切换并在 `finally` 还原（参照 `StoreSuite.cs`）。
- 验收：`合计:通过 N / 失败 0`，N 比上次数多了本套件断言数。
