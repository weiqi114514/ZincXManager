1. 架构总览

                 ┌──────────────┐
   玩家/管理员 ──▶│ ZXMC 客户端  │ 桌面程序(Avalonia,Windows)
                 └──────┬───────┘
             SAOS/OS    │            OOS(直连)
                 ┌──────▼───────┐    │
                 │ ZXMS 子服务端 │    │
                 └──────┬───────┘    │
                        │ 100/101 握手 + 600~612 账号
                 ┌──────▼────────────▼──────┐
                 │ ZXMOS 官方服务端(官方运行)│
                 └──────────────────────────┘
端项目职责
ZXMCZincXManagerClient桌面界面;连子服或官方端;消息面板与卡片;本地消息存档
ZXMSZincXManagerServer本服账号/封禁/消息/蓝图;向官方端登记身份;替客户端中转
ZXMOSZincXManagerOServer(+…NO 为早期 C++ 原型)官方社区、官方蓝图库、账号与子服登记;仅官方运行
ZXMM规划中(协议预留)模组端:在 MC 服务端里执行 ZXMS 传来的指令,未实现
  • 三端共用 ZincXManagerShared:协议常量、账号与密码哈希、命令框架、日志、网络库、官方验证。
  • 客户端三种连接方式:OS(只连子服)/ OOS(只连官方端)/ SAOS(都连;连上子服时经子服中转)。
  • 权限等级:ZXMS 侧 Player / LAdmin / HAdmin / System;官方端侧 Player / Admin / System;子服接入账号等级为占位符 -。

2. 通信协议

2.1 包结构

每包 = 长度(4 字节,含头) + 序号(4 字节) + 类型(2 字节) + 负载(UTF-8 或字节)。

收包由 Packet.ReadAsync 解析完整包后交给 PacketDispatcher 的处理器按顺序执行(处理器慢不会卡住收包)。

2.2 类型编号(三端共用,ZincXManagerShared/Network/Protocol.cs)

段编号名称方向 / 负载
1xx 子服↔官方100SOnlineZXMS → ZXMOS 子服上线握手
101SBackZXMOS → ZXMS 收到
2xx 服务端声明200ServerIdent服务端 → 对方:"ZXMS" / "ZXMOS"
201ServerName服务端 → 对方:显示名(每次接入现读 config)
202ServerConfig服务端 → 客户端:配置下发(如 msgdays)
3xx 客户端上线300ConlineZXMC → 服务端:"ZXMC:<模式>"
301CBack服务端 → ZXMC:收到
4xx 业务400/401FriendMsg/Ack未实施(编号先占)
5xx 消息500Notice服务端 → 客户端:公告卡片,逐跳原样转发
501Push服务端 → 客户端:定向推送,`目标账号卡片`,每跳按账号过滤
502CardAction客户端 → 服务端:点了卡片按钮,`动作输入原卡片`
503CardActionAck服务端 → 客户端:`ok提示 或 err原因`
504MessageHistory服务端 → 客户端:历史消息(补发)
505MessageHistoryReq客户端/子服 → 服务端:请求补发(负载 self = 收"给本端"的)
506MessageHistoryDone服务端 → 请求方:补发结束
6xx 账号600/601AccountLogin/Ack登录:`名称密文等级端机器码服务端码`

604/605AccountAvatarReq/Ack取头像(字节)/ 设置结果

521OfficialProof官方端 → 请求方:证明或 `err…`
4xx 及以上的包会被自动记进 clients.log,排查问题时先看它。

2.3 消息卡片负载

种类|标题|正文|来源|主动作|次动作|选项,种类 = text / update / choice / input / select。

动作回传:动作|输入|原卡片原文 —— 服务端用"原卡片原文"识别是哪张卡,不需要额外序号。

子服收到来源为 ZXMOS-… 卡片动作时,会在负载前多带一段账号转交给官方端。

3. 身份与账号

  • 机器码(设备):MachineCode.Value,由硬件信息派生,许可证与封禁都用它;每次启动打进日志。
  • 服务端码(实例):ZXMS 首次生成的 32 位十六进制,存 config.ini 的 servercode;丢了就会被判"身份不一致"。
  • 密码:只存密文,SHA-256(小写账号名 + ":" + 明文密码);oshash 同一套算法。
  • 账号表:
文件谁等级表
users.json子服的玩家/管理账号Player / LAdmin / HAdmin / System
osusers.json官方端的玩家/管理账号Player / Admin / System
zxms.json官方端登记的子服接入账号(等级 -)-

两张表互相查重:官方端的玩家账号与服务端账号不能同名。

  • 改名协议:AccountRename(611) 校验"账号存在 + 机器码 + 服务端码与登记一致"才允许改;

直接改 config.ini 会被判成"换了台实例",接入时报「身份不一致」。
